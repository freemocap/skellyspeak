### Proposed identity and acceptance

Conceptual names below are review vocabulary, not generated types or an IPC schema.

- **Source:** L1's immutable `message_id`, authoritative target language, and a
  nonempty half-open scalar span `[start,end)` over the exact saved source. The
  message ID is its content revision; do not invent a numeric revision. Repeated
  words at different positions are distinct occurrences. Byte/UTF-16 coordinates
  are conversions, never alternate identities. Validate ownership and endpoints
  against the saved message, not frontend-supplied text or the active selection.
- **Input:** exact whole partner passage, selected occurrence, explanation language
  captured when this explicit request is accepted, and reviewed detail/context/prompt
  versions. No conversation history, private coach text or current draft. Read exact
  text locally; provider output cannot supply or alter source IDs. Store the selected
  range itself, not an index into a replaceable array of gloss results.
- **Result slot:** source ID + scalar span + target/explanation languages + detail
  contract/context versions. `partner-gloss-v1` remains the upstream annotation
  contract, not the detail result version. Same word string in another occurrence or
  message never shares the slot. Presentation settings and selected pane are excluded.
- **Command:** use existing session/action receipt semantics for idempotent delivery.
  Repeating one action ID returns the same acceptance; changed payload conflicts.
  A database uniqueness rule also coalesces equivalent requests from different
  windows/action IDs into one live logical request. This second rule must survive
  startup clearing session receipts. Existing valid detail is returned without
  another inference attempt. Repeated requests against failed/unknown/cancelled work
  report that state; they must not silently act as Retry.
- **Operation/attempt:** operation identifies immutable captured input and execution
  authority; each explicit attempt has its own durable ID and usage. A separate
  result slot permits a replacement operation after authority/input invalidation
  without overwriting accepted detail or erasing prior attempt accounting. Route/model
  remain provenance, not word identity. Reusing an exact saved result after a route
  change makes no network call; explicit model-comparison/regeneration is outside
  this slice. If output semantics depend on model policy, version that policy in
  the slot instead of guessing equivalence.

Acceptance is one transaction: validate source/word span and supported language;
check the exact slot/live request; capture current route/model/credential authority;
check gates, holds and budgets; then create one ready network operation and command
receipt. Duplicate/read-only reuse performs no new admission. Failed acceptance
must not leave a receipt claiming success, partial operation or consumed reservation.
Do not regenerate the partner reply or attach this request to the next learner Send.

L1's `SourceMap` provides scalar/byte/UTF-16 mapping and optional boundary-ID lookup.
Its current scalar catalog is not grapheme-safe. Production acceptance requires the
reviewed grapheme gate and a valid word target; raw UI-selected ranges alone do not
establish a linguistic word. Opaque boundary IDs must resolve within the captured
source; matching `b0000` from another message proves nothing. Initial whole-source
bound: reuse L1's 4,096-scalar ceiling; reject oversize input without hidden truncation,
chunking or auxiliary segmentation calls. Keep existing transport/output limits
unless L1's reviewed detail schema demonstrates a bounded adjustment is necessary.

**Revised after integration review:** propose `DETAIL_ATTEMPT_LIMIT = 3` per logical

occurrence has its own limit; no permanent passage-wide detail cap. Existing reply /

that legacy budget. Full request-family accounting and affected functions are below.
The numerical detail limit of three is a concrete policy recommendation for
integration acceptance, not an implemented constant or a claim of provider reliability.

Requests for A and B may run concurrently and complete in either order, including
requests on the same message. A failure, cancellation or partial/unavailable content

where the result hydrates, not the current conversation selection. The accepted
partner reply remains ready for the next Send. New detail work must not set the

Store one accepted detail per result slot with its producing operation/attempt and
captured versions. Record attempt errors/unknown usage separately. Validate structured
output before committing it. A failed attempt never erases an earlier accepted
result. Any future refresh/replacement requires separate explicit semantics; it is

### R2 budget revision and implementation-sized seam review

Integration accepted independent result slots, semantic request intent,
operation-scoped controls, no synthetic turns, per-operation captured authority,
duplicate coalescing and no read-triggered retries. It rejected a permanent
16-attempt aggregate across all detail exploration of one source. The corrected
policy above supersedes that draft; R1 source remains frozen for integration review.

**Lifetime identity and limit.** Native admission assigns a durable request-family
ID with uniqueness on `(source message ID, scalar start, scalar end, target language,
explanation language, task kind = word_detail)`. Result/prompt/context versions and
route/model/credential revisions do not reset this budget identity; result slots
may be more specific. Clients cannot supply a fresh family ID or arbitrary version
to bypass the limit. Same family plus a new action ID, operation ID, credential or
application restart shares the same three-attempt allowance. A genuinely different
occurrence/source or requested explanation language is a distinct request. No
automatic language/version cycling, automatic re-plan, reset command or forced
regeneration is introduced. Deleting the authoritative source cascades its family;
creating a genuinely new edited message is a new explicit source action, not a
retry mechanism.

Count every durable network attempt recorded immediately before dispatch, including
failed, unknown, cancelled and invalidated attempts, across **all** generations in
the family. Even an attempt later discovered not to have reached HTTP remains
counted conservatively. Do not infer free retry from absent token usage. Admission
holds and rejection before attempt creation consume zero attempts. Pre-dispatch
cancel/invalidation likewise consumes no attempt; re-planning it requires explicit
intent and still uses the same family. A new generation cannot run alongside an
already active generation for that family. Preserve its attempts while the source
exists; purging old attempts must preserve a durable count if retention policy ever
changes.

In the acceptance/retry transaction, require `attempt_count + reserved_attempts + 1
<= 3` before reserving one attempt. At most one live generation/next-attempt
reservation exists for a family. Dispatch converts that reservation to its durable
attempt in the same transaction, preserving the sum. Queued/paused reservations
survive restart. Superseding an undispatched generation transfers/releases its
reservation atomically; it does not add a second allowance. A running generation
must finish or be explicitly invalidated/cancelled before replacement; its recorded
attempt remains spent. Recheck the invariant at dispatch and fail closed on an
inconsistent row, rather than silently creating attempt four.

A fourth attempt returns `AdmissionHeld` with a request-specific explanation and
zero new operation/receipt-success/HTTP. Other words remain requestable. Global
64-outstanding admission counts every ready, waiting or running detail generation
(including paused work) regardless of historical turn summary; terminal generations
release outstanding capacity. Four native permits still include transcription;
the existing 64 durable-operation queue does not count volatile audio as a new
queued detail. These concurrency/queue controls bound aggregate unfinished work,
not total lifetime exploration or requests per minute.
